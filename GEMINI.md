# SubSplit AI — Workspace Rules & Release Protocol

## 🚨 ПРОТОКОЛ РЕЛИЗА И ОБНОВЛЕНИЯ КЛИЕНТОВ (Client Release Protocol)

### 1. Золотое правило
**НИКОГДА не пушить изменения в удаленный репозиторий GitHub (`origin/main`) без явного согласия пользователя.**
Каждый раз после завершения разработки фичи, исправления ошибки или редизайна агент ОБЯЗАН спросить пользователя, нужно ли выпускать обновление для всех клиентов.

### 2. Триггеры протокола
Протокол срабатывает:
- Автоматически в конце каждого сеанса работы, когда реализована законченная фича или фикс.
- При получении явных команд пользователя: `/release`, «пушим», «выкати обновление», «залей», «обнови плагин», «сделай релиз», «деплой».

### 3. Формат запроса к пользователю
Перед пушем агент должен сформировать структурированный запрос:
```markdown
### 📦 Готово к релизу для клиентов:
- **Текущая версия**: v1.0.0 (build X)
- **Новая версия**: v1.0.1 (build X+1)
- **Что изменилось**:
  • [Краткий пункт 1]
  • [Краткий пункт 2]

👉 **Пушим обновление для всех клиентов?**
```

### 4. Алгоритм действий при подтверждении («Да / Пушим / Го / Давай»)
1. **Обновить `version.json`**:
   - Увеличить `version` (semver: patch для фиксов, minor для новых фич).
   - Увеличить счетчик `build` (+1).
   - Записать актуальное краткое описание релиза в поле `description`.
   - Обновить `releaseDate`.
2. **Проверить целостность**:
   - Убедиться, что нет лишних временных файлов (`.wav`, `.tmp`, `venv`).
   - Проверить `git status`.
3. **Закоммитить и отправить**:
   ```bash
   git add .
   git commit -m "release: vX.X.X - <описание>"
   git push origin main
   ```
4. **Уведомить пользователя**:
   Сообщить, что коммит отправлен на GitHub и при следующем открытии панели у всех монтажеров загорится бейдж «✨ Обновить» и они получат обновление в 1 клик.

### 5. Действия при отказе («Нет / Пока не надо / Позже»)
- Оставить изменения в локальном репозитории.
- Не менять `version.json` и не делать `git push`.
